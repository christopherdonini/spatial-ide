# Preregistration — time-to-first-batch: two levers, measured factorially

**Committed before the harness exists and before any measured number exists.** Same discipline as
`kernel/SCALE-PASS-PREREGISTRATION.md` and `kernel/CANCEL-RESCORE-PREREGISTRATION.md`. Every cell,
trigger, ceiling, sample count, verdict rule and invalidator below is fixed by this commit; an
amendment made after a result has been seen **must say so in its first line** and invalidates the
work it touches.

**Unattended-run rule, binding and new.** This pass runs overnight with no operator. An unattended
run **may never amend this preregistration.** A phase that cannot run as declared is recorded
`unmeasured — <reason>` and the run proceeds to the next phase. Every amendment waits for the human.

**Semantics are not defined here.** The two levers' behaviour is frozen in code and its doc comments
at commit `bf0c385`, committed first and deliberately, so this file cannot quietly redefine what it
declares a measurement of. This file declares only *what is run and how it is scored*.

---

## 0. Disclosure: this preregistration is informed by a pilot

**Stated first, because it is the thing most likely to make a reader distrust the rest.** Before this
file was written, a throwaway probe ran against the real DuckDB in this tree to establish four
capabilities. It was not a measurement of either lever and none of its numbers appear in any verdict.
It is disclosed because it **changed what is registered below** — the far-quarter viewport (§3), the
read-volume instrument (§4), and the direction of the predictions (§8) all come from it.

What the pilot established:

1. `parquet_metadata()` reports a struct child's `path_in_schema` as `bbox, xmin` — comma and space.
2. `COPY … (FORMAT PARQUET, COMPRESSION SNAPPY, ROW_GROUP_SIZE n, KV_METADATA {…})` exists here.
3. **`EXPLAIN ANALYZE` cannot evidence pruning.** Its `TABLE_SCAN` node reports post-filter *output*
   rows, which are identical with and without an id-range injection.
4. **DuckDB already prunes row groups on the covering-bbox statistics.** On the 145 MB shape a
   SW-quarter query read **77,631,970 B of a 151,642,404 B file** — 7 of 13 row groups, exactly the
   set whose envelope intersects the viewport — with no index of any kind in the path. Injecting the
   row-group-aligned id ranges on top read **77,958,433 B** in **46.00 ms** against **42.45 ms**:
   more IO and more time.

`NIGHT-CUT.md`'s premise — that parquet statistics "prune nothing today because the fixture's rows
are spatially random" — is **false in both halves**. `fixture::parcel` places feature `id` at grid
`(id % cols, id / cols)`: the fixture is **raster-ordered**, and its row groups already have narrow y
envelopes. `SCALE-PASS-PREREGISTRATION.md` §1d had already declared this as a confound. This pass
therefore measures how much DuckDB already prunes as a **first-class baseline**, not as a footnote.

## 1. What this pass may and may not claim

- **Every comparison is within-session.** No number here is differenced against any earlier section
  of `kernel/RESULTS.md`. Different session, different build, different tree.
- **B1 results are layout-variant results.** They are measured on a *different file* with a
  *different content hash* and may never be stated as a same-file claim.
- **A plan is not evidence of IO exclusion.** "The predicate was built" and "IO was excluded" are
  different facts. The second section's mistake was to time the first while believing the second, and
  this pass separates them by instrument (§4).
- **Build cost and query benefit are never netted.** No "pays for itself after N queries" appears.
- **No throughput claim.** Bytes and durations are recorded side by side and never divided.

## 2. The fixtures, and what is verified before anything runs

Generated by this harness, in this session, from the committed generator and seed. Every file's
SHA-256 is recorded in the artifact **before** the trial loop and re-verified after the last trial.

| id | shape | writer | order |
|---|---|---|---|
| `S` | 100 000 features, avg 100 vertices, `row_group_rows = 8_192` → 13 row groups | arrow-rs `ArrowWriter` | raster by id |
| `C` | the same rows, rewritten | **DuckDB** `COPY`, `ClusterOrder::SourceIdentity` | raster by id |
| `H` | the same rows, rewritten | **DuckDB** `COPY`, `ClusterOrder::Hilbert16` | Hilbert order 16 |

**`C` exists because without it lever B1 is confounded, and this is the pass's most important piece
of setup.** A clustered variant is written by DuckDB's parquet writer; the fixture it is made from is
written by arrow-rs. Compression matches, but page size, dictionary thresholds, encodings and
statistics emission do not. **B1's comparison is `H` against `C`, never `H` against `S`** — that pair
differs by the row order and by nothing else, because both come from the identical `COPY` statement
with only the `ORDER BY` changed.

`S` against `C` is itself a **registered cell**: it prices the writer difference, so the size of the
confound that would have been attributed to layout is a measured number rather than an argument.

`row_group_rows = 8_192` is a multiple of DuckDB's 2 048-row vector size. That is not incidental: the
writer flushes on such a multiple, and `write_clustered_variant` refuses outright when the written
layout does not match the requested one. A refusal here stops the B1 phase; it does not get worked
around.

**The 5 GB spot cells reuse `target/slice-evidence/scale-pass/parcels-5gb.parquet` if it is present
and verifies, and generate it otherwise.** Disk headroom ≥ 20 GiB is checked at the phase boundary
before any 5 GB work; below it the phase is `unmeasured — insufficient disk headroom`.

## 3. The factorial, and the viewport that had to be added

```
{batch: size-only, budgeted} × {file: S, C, H} × {plan: ScanOnly, RowGroups}
                              × {viewport: whole, near-quarter, far-quarter, 1/64}
```

with the **declared exclusions**, each for a stated reason rather than for cost:

- `plan: RowGroups` on `H` is **structurally impossible**: clustering destroys the identity ordering
  the injection needs, and the engine refuses it by name (`IdRangesOverlap`). One cell is run anyway,
  once, to record that the refusal is what actually happens rather than what is predicted.
- `plan: RowGroups` with `viewport: whole` emits no predicate by construction. One cell is run to
  record `FilterPlan::WholeFile` and zero metadata work, which is a **gate condition** for B2 (§8).
- `file: C` is measured under `ScanOnly` only. It is a writer control, not a lever.

**The far-quarter viewport is new and it is the only cell in which lever B2 can act.** Every viewport
this repository has registered is south-west anchored, so on a raster-ordered file its matching rows
are at the **front** of the scan, while row-group elimination removes work from the **tail**. Without
a viewport whose rows are at the tail, B2's effect on time-to-first-batch is answered by arithmetic
rather than by measurement. The far quarter has the same x band and a y band at the top of the
extent; both edges land on a cell **centre**, so inclusion is pure arithmetic and cannot depend on
per-feature vertex jitter — the correction `scale_pass.rs::viewport_edge` records.

Each viewport's **exact predicted row count is asserted by the harness**. A mismatch is an
**instrument failure that stops the phase**, not a result.

`n = 7` admitted trials per cell. **A floor, not a target.** A cell that cannot reach 7 is reported
`unmeasured — n < 7` and is not scored.

**One process per trial.** The index and metadata caches are process-wide and path-keyed, so a B2
trial warms a cache a later ScanOnly trial cannot un-warm; and `trace::start` refuses a second
concurrent trace, so one-process-per-trial makes the "one traced stream per traced run" limit free.

**Interleaving is generated by a committed pure function, never a runtime shuffle** — a shuffle is
not reproducible. Repetition `r` runs cell `cells[(i + 5r) mod N]`.

## 4. Instruments

| quantity | instrument | notes |
|---|---|---|
| time to first batch | producer wall clock, `stream()` call → first `next_into` return | the budget-bearing figure |
| total | outer wall clock | **never** derived from a trace |
| rows, payload bytes | `BatchInfo` | identical across plans or the cell is inadmissible |
| which policy ran | `BatchStream::size_policy().cut`, `filter_plan()` | reported, never inferred from a timing |
| which trigger cut each batch | `BatchInfo::cut_by` | how "did lever A fire?" is answered |
| **IO actually read** | **`GetProcessIoCounters` read-volume delta across the query** | see below |
| segment breakdown | producer trace spans | traced twins only; see §5 |

**The read-volume instrument, and why it replaces the one the architect declared.** The architect's
declaration named `EXPLAIN ANALYZE` scan cardinality as the pruning evidence. §0 finding 3 shows that
instrument does not measure what it was declared to measure. It is **withdrawn and replaced** by the
process's own read-byte counter, taken immediately before and after the query in a process that runs
exactly one query.

Its limits, declared now rather than after a result:

- **Windows-only.** A bare `extern "system"` declaration against kernel32 — zero new dependencies.
  On any other platform the cell is `unmeasured — instrument unavailable`, and nothing about macOS or
  Linux follows from this pass, exactly as `docs/07` limits ADR-003.
- It counts **logical** read bytes issued by the process, warm OS file cache included. It is
  therefore evidence about *what the query asked the file system for*, which is precisely the
  IO-exclusion question, and it is **not** evidence about physical disk traffic. No claim about disk
  is available to this pass.
- It is a whole-process counter. One query per process is what makes it attributable.

## 5. Trace-on/off policy

`TRACE_BUFFER_RECORDS = 4096`, dropped **positionally**. At the 145 MB class a whole-file stream is
roughly 195 batches, so the buffer does not fill; at 5 GB whole-file it does (6 637 batches, ~2 547
dropped). Both facts are checked in the artifact via `dropped_records`, not assumed.

- **Every budget-bearing 145 MB cell runs untraced, with a traced twin beside it.** The sixth section
  could not establish its null-overhead result at this repository's own n ≥ 7 floor, so a verdict
  resting on a traced cell would rest on an unestablished null. **Untraced carries the verdict;
  traced supplies the decomposition.**
- Traced twins: n = 7 at the two quarter viewports (the gate viewports); n = 3 at whole and 1/64,
  labelled *not verdict-bearing, n = 3*.
- 5 GB spot cells run untraced, plus one traced first-batch-only trial per cell.
- **Segments derivable from a trace with `dropped > 0`: exactly `query` and `source_to_first_batch`,
  and nothing else** — `trace.rs`'s own replacement rule. `dropped_records` prints beside every
  trace-derived number.

## 6. Correctness: what is compared, and how

`NIGHT-CUT.md` asks for "exactly the same rows and byte-identical payload". The second half is
**unachievable for B1 and unguaranteed for B2** — `RowOrdering::Unordered` promises no order, and a
layout variant necessarily has a different one. Asserting it would fail for reasons unrelated to
correctness, and quietly weakening it later is the drift this repository guards against. It is
replaced by three distinct assertions:

| comparison | assertion |
|---|---|
| **within a cell** (7 trials, one plan, one file) | SHA-256 over the concatenated wire bytes **equal across all 7**. A mismatch invalidates the cell and is a finding ahead of every timing |
| **across plans, one file** | row count identical · **sorted per-feature digest set `{(id, sha256(coords))}`** identical · total geometry bytes identical. Concatenated-stream byte-identity **recorded if observed, not required** |
| **across files** (`S` / `C` / `H`) | the same sorted per-feature digest set, and the same row count |

The digest set is **strictly stronger** evidence of "exactly the same rows" than a concatenation
hash: it is a byte-level identity of every geometry, order-independent by construction.
`coord_bits_xor` may be reported beside it as a cheap corroborating reduction and **never** as the
primary check — being an XOR, it is invisible to a coordinate swapped between two features.

**Lever A's determinism assertion, separately:** publish the same inputs under a build carrying the
budgeted policy and confirm manifest and every partition byte-identical. The structural half — that
`stream_for_publish` cannot acquire the budgeted policy — is already a compile-and-test property at
`bf0c385` and is not re-measured.

## 7. Admissibility, canary, and declared invalidators

**A cell is admissible iff** all of: source pin and binary pin identical before and after the phase ·
free disk ≥ 20 GiB at the phase boundary · the phase's canary spread ≤ 10 % (**per phase, never
global**) · the cell's observed `filter_plan` and `cut` policy are the ones it declares · row count
equals the prediction · fixture hashes verified before the trial loop · n = 7 admitted trials.

**Canary/settle, inherited verbatim:** a 400 M-iteration long instrument at the start and end of
every phase · **120 s opening settle** before the first canary · **60 s settle before every canary
reading** (scale-pass amendment A1) · the pre-settle reading recorded and excluded from the spread.
Every cell here carries a timing comparison, so every cell is canary-gated.

**Invalidators.** Any of: a fired watchdog (the row becomes `unmeasured — watchdog at N s`; the phase
is **not** re-run in this cut) · a trial whose `filter_plan` differs from the cell's declaration —
that is an **observation, not a sample**, and is not promoted into the cell's statistics · a
within-cell wire-byte mismatch · a fixture hash mismatch · a `write_clustered_variant` layout refusal.

**Declared watchdog ceilings**, before measuring: generate `S` 600 s · rewrite `C` or `H` 900 s ·
build a row-group index 300 s · one 145 MB trial 120 s · one 5 GB trial 900 s · generate 5 GB 1800 s.
Silence ceiling on any streaming phase 120 s.

## 8. The gates, and the registered predictions

**"Beat" is defined before the run**, on the third section's own practice: **p50 lower *and* ≥ 42 of
49 pairwise comparisons** rank-separated at n = 7 vs 7. A p50 delta alone is not a pass.

**Lever A** enters the default planner iff, at some registered cell, it beats the size-only twin on
the same file and plan at time-to-first-batch, with identical digest sets, **and** `cut_by` shows
`time-budget` on batch 0 in all 7 trials of that cell. A cell where the budget never fires is not a
pass and is not a failure — it is a null, and it is what §8's prediction expects.

**Lever B2** enters the default planner iff **all** of: plan is `RowGroupsPruned { kept < total }` in
all 7 trials of the gate viewport · **pruning evidenced by read volume strictly lower than ScanOnly's,
same session, same viewport** · first-batch p50 lower and 42/49 at the **far quarter** · digest sets
identical and row count equals the prediction · no whole-file regression, and whole-file reports
`FilterPlan::WholeFile` with zero metadata work · metadata build cost reported separately and never
netted.

**Lever B1 cannot enter the default planner — there is nothing in the planner to switch.** Its gate
is: same-session `ScanOnly` on `H` beats same-session `ScanOnly` on **`C`** (not `S`) at quarter-extent
time-to-first-batch, p50 and 42/49, with identical digest sets. **A pass yields a proposed ADR on
ingest-layout policy, not a code change in this cut**: reordering a user's file at import is new
product behaviour with its own reproducibility grade (ADR-005) and its own recorded-operation
obligation (`docs/05`), and that is architect-first work.

### Registered predictions, committed before the run

Made from arithmetic and the §0 pilot, so this pass is a test rather than a fishing expedition. Being
wrong about any of them is a result, not an embarrassment.

1. **Lever A is predicted null at both classes.** At `avg_vertices = 100`,
   `estimate_bytes(1, 100) ≈ 2 012 B` per row, so a 64 KiB first batch is ≈ 33 rows — far inside one
   2 048-row DuckDB chunk. The budget can fire only where DuckDB returns partial vectors, which the
   sparse 1/64 and far-quarter cells may do and the whole-file cell will not.
2. **Lever B2 is predicted to exclude no IO that DuckDB does not already exclude**, and to cost a
   longer statement. §0 finding 4 is the evidence; the far quarter is where it gets its fairest test.
3. **Lever B1 is predicted to *lose* at the quarter viewports and *win* at 1/64, at this class.**
   Measured directly from the files' footers before the run: row groups a viewport must read,

   | shape | near quarter | far quarter | 1/64 |
   |---|---|---|---|
   | 100 000 features, 13 groups, raster | **7 / 13** | **7 / 13** | 2 / 13 |
   | the same, Hilbert16 | 8 / 13 | 7 / 13 | **1 / 13** |

   **The mechanism:** raster order's row groups are full-width strips, so a viewport costs its
   *height*; a curve's row groups are compact blobs, so a viewport costs its *area plus a boundary
   term*. At a quarter viewport (half the extent each way) height ≈ 50 % beats area-plus-boundary; at
   1/64 the area term wins.
4. **The sign of prediction 3 is predicted to flip with row-group count.** The boundary term shrinks
   as groups get smaller: at 13 groups a blob is ≈ E/3.6 against a viewport of E/2 and the boundary
   dominates; at the 5 GB class's 403 groups a blob is ≈ E/20 and the interior term should dominate,
   putting the curve ahead at the quarter. **This is the single most interesting thing this pass can
   test**, and it is registered now.

## 10. The outcome this pass is pre-authorized to reach

**"Neither lever passes its gate" is a legitimate and complete result**, and given §8's predictions it
is the expected one. If it happens, the levers stay out of the default planner, the fixed-grid
index's planner note stands unchanged, and the pass's value is the four things it will have
established that no document in this repository currently states:

1. How much DuckDB's own zone maps already prune on a multi-row-group GeoParquet, measured in bytes.
2. That an external row-group index over the same statistics is redundant with that, or is not.
3. That storage layout trades a viewport's *height* against its *area*, with the crossover located.
4. That spatial clustering and identity-range pruning are mutually exclusive on one file.

None of those needs a lever to pass, and all four bear directly on `docs/07`'s open "index that prunes
actual IO" item.

### A1 — 2026-08-08 — the 5 GB clustered cell, authorized by the human after results were seen

**This amendment was written after the run of record and after its verdicts were read.** That is
stated first because this document requires it, and because it is the fact a reader most needs in
order to weigh what follows. It is written *by* the operator's explicit authorization, not by an
unattended session deciding its own scope — §0's unattended rule held, the phase waited, and the
human is present.

**It changes no trigger, no ceiling, no sample count and no verdict rule, and it carries no number
from the completed pass forward into a new verdict.** The double-null verdict of the seventh section
stands exactly as written: **neither lever enters the default planner.** Nothing below can change
that, and nothing below is permitted to be cited as though it could.

#### What it adds, and why it could not have been declared earlier

§8 registered **prediction 4**: that finding 4's height-versus-area crossover **moves with row-group
count** — raster's full-width strips cost a viewport its *height* at every granularity, while a
curve's blobs cost its *area plus a boundary term* that shrinks as groups get smaller. At **13** row
groups the curve lost 0 of 49 at a quarter; at **403** the arithmetic says it should win.

The seventh section established **half** of that: the raster baseline does **not** improve with
row-group count (50.5 % of the file at 403 groups against 51.8 % at 13). The other half — whether the
curve's boundary term actually shrinks — is untested, and testing it needs a Hilbert rewrite of a 5 GB
file that §9 placed out of scope because `NIGHT-CUT.md` scoped 5 GB cells to "ScanOnly vs **the
winning** pruning candidate" and no candidate won. **The human has now placed it in scope explicitly.**

#### Cells

**Two new 5 GB files, and the second is not optional.** The seventh section's most expensive lesson is
that a clustered variant comes from DuckDB's writer while the fixture it is made from comes from
arrow-rs, and that the writer alone moved whole-file first batch by 20.1 ms — larger than the layout
effect it would have been mistaken for. So the 5 GB comparison gets the same control:

| id | writer | order | source |
|---|---|---|---|
| `S5` | arrow-rs | raster by id | the scale pass's own fixture, **reused and never written to** |
| `C5` | DuckDB `COPY`, `ClusterOrder::SourceIdentity` | raster by id | rewritten from `S5` |
| `H5` | DuckDB `COPY`, `ClusterOrder::Hilbert16` | Hilbert order 16 | rewritten from `S5` |

`row_group_rows` = **8 192**, the scale pass's own value and a multiple of DuckDB's vector size;
`write_clustered_variant` refuses any layout it did not produce as asked, and that refusal stops this
phase rather than being worked around.

**Factor levels:** `{S5, C5, H5} × {whole, near-quarter, far-quarter, 1/64} × ScanOnly × size-only`,
n = **7**, one process per trial, interleaved by the same committed pure function. **12 cells,
84 trials.**

**Only the size-only batch policy runs, and the omission is declared rather than silent.** Lever A is
answered — zero budget cuts in 426 trials across two classes — and re-running it here would add half
again as much wall-clock to re-establish a null this pass already holds at n = 7 in six cells. **This
amendment may not be read as evidence about lever A in either direction.**

**1/64 is included** because it is the other side of the crossover: it is where the curve won at 13
groups, and prediction 4 is a statement about how the two viewport sizes trade as granularity changes.

#### Row counts, predicted by arithmetic **before** the phase runs

The seventh section recorded (S13) that its row-count check was a same-instrument tautology — the
reference count came from the same engine, the same predicate and the same fixture as the trials, so
it could catch nondeterminism and not a wrong filter. **That is corrected here**, on the fifth
section's precedent: from the generator's grid (`cols = ⌈√3 300 000⌉ = 1817`, 40 m cell, the last
grid row holding 3 300 000 − 1816 × 1817 = **328** features), the exact counts are

| viewport | derivation | rows |
|---|---|---|
| whole | — | **3,300,000** |
| near quarter | 909 columns × 909 rows | **826,281** |
| far quarter | 909 × 908 full rows + 328 in the partial last row | **825,700** |
| 1/64 | 228 × 228 | **51,984** |

Two of these are the fifth section's own registered numbers, arrived at independently. **A mismatch
is an instrument failure that stops the phase**, not a result.

#### Gate, unchanged

B1's gate is **`H5` against `C5`** — never against `S5` — at the **quarter** extent, p50 lower **and**
≥ 42 of 49 pairwise, with row counts equal to the arithmetic above. `S5` against `C5` prices the
writer at this class. **A pass yields a proposed ADR on ingest-layout policy, not a code change**, and
it does not disturb the seventh section's verdict that nothing enters the default planner today.

#### Ceilings and protocol, unchanged

120 s opening settle; 60 s before every canary reading; ≤ 10 % per-phase spread; disk ≥ 20 GiB checked
at the phase boundary; one 5 GB trial ceiling 900 s; rewrite ceiling 1800 s per file, raised from §7's

nothing to the scale pass's directory.

#### What this phase may not claim

- **No comparison with the seventh section's 145 MB numbers, or with the fifth section's**, in either
  direction. Its own three files, in its own session, or nothing.
- **No timing comparison across phases.** The byte-counter carve-out the seventh section declared

- **Nothing about lever A**, which does not run here.
- **Nothing about the default planner.** B1 is a layout candidate; there is no planner switch.

### A2 — 2026-08-08 — the browser-probe cells, authorized by the human after results were seen

**Written after the run of record and after its verdicts were read**, like A1 and for the same reason:
this document requires an amendment to say so first. The probe cells were deferred by
`NIGHT-CUT.md`'s rule 3 — they need a visible window — and that rule deferred them **without ever
specifying what they were**. So this is not a re-scoping of something declared; it is the declaration
that was owed.

**It changes no trigger, no ceiling, no sample count and no verdict rule.** The seventh section's
double null stands: neither lever enters the default planner, and **no probe cell can change that,
because no gate is scored here.**

#### The one question these cells exist to answer

The producer-side pass found exactly one measured layout win: at the **1/64** viewport the clustered
file reads **12,870,243 B against 25,146,407 B** and beats its control 45–47 of 49 on time to first
batch. Every other lever result is a null.

The third section decomposed first pixels and found the budget spent before the browser runs: S2
(query start → OPEN) 67.8–103.7 ms, S4 + S5 under 11 ms in four of seven cells. **So a 1.3 ms
producer-side win has somewhere to disappear**, and whether it survives to a pixel is a different
measurement from whether it exists. That is the whole question.

#### Cells

`{S, C, H} × {quarter, 1/64} × {headless, headed}`, **n = 7**, one page load per trial. **12 cells,
84 page loads.**

- The three **145 MB files of the run of record**, unchanged and re-hashed before the phase. B1's
  comparison remains **`H` against `C`**, never against `S`; `S` against `C` prices the writer on
  this path as it did on the producer's.
- **Headless and headed are separate cells and are never pooled** — `PROBE-PREREGISTRATION.md` §1a's
  rule, because headless changes the compositor and GPU path.
- **Whole-file is excluded.** It is where the writer effect was largest producer-side (20.1 ms) and
  where no layout effect exists, so it would spend a third of the human's attention on a cell whose
  answer is already known. Declared, not dropped.
- The **display** extent is held fixed at the fixture's full extent in every trial, so only the query
  changes and the draw transform does not.

Segments, instants and invalidators are **`PROBE-PREREGISTRATION.md` §1a and §2 verbatim**. Nothing
here redefines a boundary.

#### What these cells may not claim

- **No gate.** B1's gate was decided producer-side and is closed. A probe result cannot open it, and
  a favourable probe cell is not a second chance at it.
- **No comparison with the third section's numbers**, in either direction. Different session,
  different tree, different fixture class.
- **No comparison with the producer-side first-batch figures in the seventh section.** They are a
  different quantity on a different clock in a different process. What the probe can say is whether
  the *sign* of the layout effect is still visible at the pixel; it cannot say the two magnitudes
  agree.
- **Nothing about lever A or lever B2**, neither of which the browser path can reach: `slice-host`
  never calls `build_index`, so every browser trial is `ScanOnly` or `WholeFile` — §1a's
  "structurally absent, declared absent rather than reported as zero".
- **Nothing about frame time or the renderer module.** The probe is a 2D canvas consumer.
- **Nothing about macOS or Linux.**

#### The outcome this phase is pre-authorized to reach

**"The producer-side layout win does not survive to first pixels" is a complete and expected
result.** A 1.3 ms difference against an S2 that the third section measured at 67.8–103.7 ms may well
be invisible, and if it is, that is worth knowing precisely: it would say that storage layout is a
*total-time* and *IO* lever rather than a first-pixels one, which is a sharper claim than the
producer-side pass alone can support.

#### A2.1 — 2026-08-08 — four additions to A2, from the operator, still before any probe trial runs

**Written after the producer-side results were seen and before any probe cell has run.** The
distinction matters here more than in A1 or A2: item 2 below is a **verdict rule**, and it is being
fixed while the data it will judge does not yet exist.

**1. Counterbalancing — layouts interleave *within* each viewport × compositor block.** Not
file-by-file. The order inside a block is a rotation over `{S, C, H}` by repetition index, the same
committed-pure-function discipline the producer-side pass used, so no layout systematically occupies
the warm or the cold end of a block.

**This is also why no separate re-baseline phase exists**: the `S` cells **are** the same-session
control. A re-baseline run before or after the layout arms would be a different block of time on a
machine this repository has measured drifting by a factor of two between phases twenty minutes apart.

**Headless runs first, unattended. Every headed cell is scheduled contiguously**, so the operator's
window-sitting is one stretch rather than six.

**2. The resolvability criterion, declared now, before any probe number exists.**

The third section recorded the probe's own between-attempt dispersion: **up to 29 ms on a
first-pixels p50**, across attempts of the same cell on the same tree. That is the instrument's
noise floor and it is not reducible by anything this phase can do.

> **Any first-pixels difference smaller than 29 ms on p50 is reported as `not resolvable by this
> instrument`.** Not "no effect", and not a win. Both of those are claims this instrument cannot
> support at that scale, and the whole point of declaring it now is that the wording is chosen before
> anyone can see which way it would flatter the result.

Applied to both comparisons this phase makes:

| comparison | producer-side size | verdict available from the probe |
|---|---|---|
| **`H` − `C`**, the layout arm, at 1/64 | **1.3 ms** | **predicted `not resolvable` in advance.** 1.3 ms is more than twenty times below the noise floor. If a probe cell shows a large difference here it is evidence about the *instrument or the session*, not about layout, and it will be read that way |
| **`C` − `S`**, the writer arm, at the quarter | **5.1 ms** producer-side (whole-file was 20.1 ms and whole-file does not run here) | **may or may not resolve.** Also below the floor; the same rule applies |

**So this phase is registered as most likely to produce two `not resolvable` rows, and that is a
result.** It would establish that storage layout is an **IO and total-time** lever and not a
first-pixels one at this fixture class — a sharper claim than the producer-side pass can make alone,
and one that cannot be made at all without this criterion having been written down first.

**A difference at or above 29 ms would be a finding and would still not open B1's gate**, which was
decided producer-side and is closed.

**3. Layout arms use the night's existing artifacts only.** `S`, `C` and `H` as written by the run of
record, re-hashed before the phase. **No new layout variant is generated for a probe.** A file
produced to be measured by the instrument that will measure it is the confound this whole cut spent
its most expensive lesson on.

**4. Full-payload is printed beside first-pixels in every cell, always** —
`PROBE-PREREGISTRATION.md` §1a's rule, never one without the other. **The 5 GB file does not enter
the browser at all**, in any cell, under any compositor.
