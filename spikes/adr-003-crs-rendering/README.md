# Spike — ADR-003: Arbitrary-CRS Rendering

**Question:** can deck.gl inside a Tauri webview render and edit large datasets in a projected CRS (EPSG:2056) with centimetre picking accuracy — without converting to Web Mercator?

**Stakes:** the only open technical gate in the constitution (docs/adr/ADR-003). Pass → deck.gl is the projected working canvas. Fail → purpose-built WebGPU renderer for the projected canvas; Tauri shell unaffected either way. Both outcomes are wins — the failure mode is *not knowing*.

## Acceptance gate (from ADR-003)

> Load and interactively edit a large dataset in EPSG:2056 **without permanently converting it to EPSG:3857**, maintaining centimetre-level picking accuracy, within docs/08 budgets, on all three system webviews.

This spike proves Windows/WebView2 first; macOS (WKWebView) and Linux (WebKitGTK) run in CI before the ADR flips to accepted.

## Technical approach

- deck.gl `OrthographicView` over raw projected metres — no geographic projection in the view at all.
- **Offset-relative rendering** is where precision lives or dies: EPSG:2056 eastings ≈ 2.6×10⁶ m; float32 carries ~7 significant digits, so absolute coords lose centimetres. Re-center on the view origin (f64 math kernel-side, or deck.gl `coordinateOrigin`) before f32 GPU upload.
- Data path: Rust generates/loads → Arrow IPC → webview via custom protocol / binary channel (**no JSON, even in the spike**) → binary attributes into deck.gl layers.
- Picking: GPU pick → feature id → resolve exact f64 coordinate on the Rust side; compare against ground truth.

## Test data (synthetic first, generated — never committed)

EPSG:2056 extent: E 2,485,000–2,834,000 · N 1,075,000–1,296,000.

- **P1** — 10M random points, uniform over extent
- **P2** — 100k "parcel" polygons / ~10M vertices (perturbed grid)

Real data later: swisstopo open data (cadastral surveying, swissTLM3D) for the final validation run.

## Milestones

- **M0** — Tauri v2 app boots; log renderer availability (WebGL2/WebGPU), GPU adapter info from inside WebView2.
- **M1** — P1 rendered via Arrow → binary attributes; pan/zoom ≥ 60 fps p50, measured p95.
- **M2** — Precision: no vertex jitter at 1:500 zoom anywhere in the extent; screen-space error < 0.5 px.
- **M3** — Picking: click → feature id + exact source coordinate; error < 1 cm.
- **M4** — P2 polygons + vertex-drag editing; precision and frame rate hold during edits.
- **M5** — Data-plane audit: count every copy end-to-end (Rust → IPC → JS → GPU), MB/s throughput, cancellation < 100 ms mid-load (ADR-004 honesty check).

## M3 metric definition (written before measuring)

Recorded here ahead of the harness so the target cannot be quietly reinterpreted to fit whatever comes out.

**Picking error = |returned f64 coordinate − true f64 coordinate of the *intended* feature|**, where *intended* is the feature nearest the click point.

What the < 1 cm target therefore tests:

1. **Id-resolution correctness** — the GPU pick returns the index of the feature the user actually aimed at.
2. **f64 round-trip exactness** — that index resolves, Rust-side, back to the stored source coordinate with no precision lost in transit.

What it explicitly does **not** test: sub-pixel unprojection. At 1:500 one pixel is 0.132 m, so 1 cm is **0.076 px** — recovering a centimetre by unprojecting a click position is arithmetically impossible per-pixel, and any harness that appeared to achieve it would be measuring something other than what it claimed. This is why ADR-003 specifies "GPU pick → feature id → resolve exact f64 coordinate on the Rust side" rather than unprojecting the cursor: the coordinate is *looked up*, not *reconstructed*.

The consequence is that the metric is close to bimodal by construction. Correct id + exact round-trip gives error identically 0. A wrong id gives the distance to whichever feature was returned instead — in the 0.1 m marker grid that is ≥ 10 cm, an order of magnitude past the budget. So < 1 cm is in practice a correctness assertion with a small tolerance for round-trip loss, not a continuous accuracy measurement, and it should be read that way.

**Three click classes**, all under `offset-dynamic` rendering at the five M2 probe locations:

- **(a) Dead-centre on isolated features** — requires the correct id and a bit-exact f64 round-trip.
- **(b) Offset by 1–3 px** — requires deterministic nearest-feature selection; the intended feature is still the nearest one.
- **(c) Dense pairs** at decreasing separation, starting from the 0.1 m marker-grid spacing (0.76 px at this scale) — measures **the separation at which id discrimination becomes reliable**. That separation is a *finding to be reported, not a pass/fail*: two features 0.76 px apart cannot be distinguished by a pixel-resolution pick buffer, and the useful output is the number at which they can.

Additionally recorded: whether the returned coordinate touches f32 anywhere on its path (it must not — the render path narrows to f32 for the GPU, but the pick path is index → f64 lookup and never reads a rendered position).

## M4 scenario definition (written before measuring)

Recorded here ahead of the harness, same discipline as M3's metric definition: the target cannot be quietly reinterpreted once numbers exist.

**The ≤16 ms budget applies to a declared, geometry-derived viewport, not to full P2.** M2/M3's own precedent is to derive geometry from a declared scale + framebuffer rather than pick a feature count first — and their 1:500 scale is a category error here: at 0.1322917 m/px, a single ~872.5 m × 884 m parcel cell would span ~6,600×6,680 px, far larger than any framebuffer. M2/M3 exist to test sub-pixel *point* precision; M4 is a parcel-scale editing/throughput scenario and needs its own scale. Declared: **1:20,000** (M_PER_PX = 5.2916667, PX_PER_M = 0.1889763), on the spike's actual native window — 800×600 (`tauri.conf.json`), confirmed empirically by M2/M3 and re-confirmed (not assumed) by M4's own settle-and-pin step, identical in method to M2's "waited for a settled size, pinned, and re-checked for mid-run resize."

**P2 layout** (`src-tauri/src/p2.rs`): a 400×250 grid of cells over the same EPSG:2056 extent as P1 — **exactly** 100,000 polygons (matches docs/08's polygon budget class), each an inset rectangle (10% margin, so parcels never touch) walked at 100 vertices per side-proportional step (25/side) with independent ±3 m jitter per vertex (safe against both the ~28 m average inter-vertex spacing and the inset margin — no self-intersection, no neighbour-cell crossing) — **exactly** 10,000,000 vertices. Cells are ~872.5 m × 884 m.

**Visible subset**, derived from the declared geometry rather than picked first: at 1:20,000 on an 800×600 window, the on-screen ground extent is ~4,233 m × ~3,175 m, centred on the polygon nearest the extent centroid ("the edit target," resolved from grid indices at runtime, not hardcoded). Against ~872.5×884 m cells that predicts on the order of **5 columns × 3-4 rows ≈ 15-20 polygons (~1,500-2,000 vertices)** — a genuinely small, zoomed-in fraction of P2 (≈0.02% of its polygons). The exact count comes from a polygon-centroid bbox filter (`p2.rs::arrow_ipc_bbox`, an O(100k) polygon-level scan, not O(10M) vertex-level — 100× cheaper than P1's own bbox scan for the same reason M1.5 flagged P1's as a confound) and is **logged, not assumed** — matching M1.5's "999,841 / 10,000,000" convention rather than rounding to a clean number that pixel alignment might not actually produce. This subset is what the ≤16 ms budget is graded against.

**Full-P2-visible drag is a reported finding, not the pass/fail** — same framing M1 used for the full-10M-point pan/zoom miss: informative about the ceiling, not something M4 is expected to pass.

**Layer design — two layers, not four.** P2 is rendered as its vertex sets only (`ScatterplotLayer`, the same binary-attribute idiom P1/M2/M3 already use), not as filled or outlined shapes: M4's ask is about vertex-drag editing mechanics (the static/overlay split, picking, origin-swap/commit cost), not polygon rendering fidelity, and a `PathLayer` outline would double every buffer this milestone measures (a closing-vertex duplicate per polygon, plus `startIndices` bookkeeping) without changing any of the three quantities M4 is asked to measure. "Polygon" lives in the data model (100 vertices grouped by id arithmetic — `polygon_id = id / 100`, `vertex_index = id % 100`; no separate id array stored server-side, since storage is polygon-major and the mapping is arithmetic) and in the generation method (perimeter walk), not in the render style.

- **Static layer**: every vertex not currently being edited. Built once per scenario (visible-subset or full-P2) and **never rebuilt during a drag** — its `data`/attribute-value reference is reused by identity for the whole interaction, so per M2's own documented finding ("the data object is reused by reference so the attribute buffer is never re-uploaded"), it costs nothing per frame regardless of size. This is deliberately literal: the static buffer is not even patched to exclude the polygon being edited, because doing so would itself cost a rebuild proportional to the static set's size — trivial at visible-subset scale (~2,000 vertices) but a real ~10M-vertex-scale cost at full-P2 scale, i.e. exactly the class of cost the origin-swap test below exists to measure, and paying it twice (once to exclude at grab-time, once again to include at commit-time) would be worse than paying it once, at commit.
- **Overlay layer**: the one actively-edited polygon's 100 vertices, rebuilt every frame from a **fresh** `Float32Array` (not mutated in place — deck.gl's diffing is reference-based, so an in-place mutation without a reference change risks a silently-stale GPU buffer, the same mechanism M2 relied on for the opposite purpose). Always the **last** element of the `layers` array passed to `setProps`. Consequence: the static layer's stale pre-drag position for the edited polygon remains visible underneath as a harmless double-draw for the drag's duration, and per M3 diagnostic note 3 ("the picking buffer keeps whichever fragment drew last"), the overlay's live vertex — not the static ghost — is what a pick returns wherever the two coincide or overlap. This is asserted at runtime (`overlayWinsCollision`), not just assumed.
- **Commit (pointer release)**: `commit_vertex_edit(id, e, n, crs)` sends the new f64 coordinate to Rust, tagged `"EPSG:2056"` and rejected host-side if the tag doesn't match (the write-path mirror of `resolve_pick`'s outbound tagging — a mislabeled frame here would corrupt ground truth, not just misreport a click). A follow-up `resolve_p2_vertex(id)` read-back asserts the stored value round-trips bit-exact, M3-style. Client-side, the static buffer's one polygon is patched: **not** the same operation as the origin swap below, and deliberately distinguished rather than conflated — an origin change moves *every* vertex's local offset, so it needs an O(N) CPU rebuild; a commit changes exactly one vertex's world coordinate, so it only ever needs an O(1) CPU patch (write two floats into the existing buffer). What the two share is the part chunking can't help: deck.gl has no partial-attribute-update API, so *any* change signal reuploads the whole static buffer to the GPU — an O(N) cost regardless of how many values actually changed. At **visible-subset** scale (~2,000 vertices) that reupload is cheap and measured directly. At **full-P2** scale it is the same order of magnitude as the origin-swap test's own GPU-reupload measurement, so that number is reused rather than re-derived from scratch — but the CPU-side chunked-rebuild mitigation is specific to the origin-swap's O(N) rebuild and is not needed (or applicable) here.

**Drag path**: authored in absolute f64 EPSG:2056 around the dragged vertex's true coordinate (a small synthetic circle, radius 2 m, self-driven the same way M1/M1.5/M3 self-drive pan/zoom/clicks — no browser-automation path reaches the native WebView2 window), then run through `OffsetFrame`/`offsetPositions` exactly like every other coordinate in this spike. Stated explicitly because M3 diagnostic note 1 found a local-frame value can cross a boundary "wearing a coordinate's clothes" — the drag path is never authored directly in local/screen space.

**Precision is re-checked, not assumed carried over from M2.** M4 is the first milestone with a *write* path; nothing in M2/M3 validates that the overlay's per-frame fresh-buffer-reupload strategy holds the same sub-pixel guarantee. A small M2-style check (predict the dragged vertex's framebuffer position in f64 independently of deck.gl, capture via `readPixels`, intensity-centroid) samples a few frames during the drag against the same <0.5 px budget M2 used — duplicated rather than imported from `m2-precision.ts`, per this spike's established convention of keeping each milestone's committed numbers independent of modules a later milestone might change.

**Pick-to-grab latency**, measured three ways at the same predicted screen pixel (repeated `pickObjectAsync`, p50 of ~20 calls): against the **full 100k-polygon/10M-vertex** vertex layer (unfiltered — explicit worst case), against the **overlay** (~100 vertices — explicit fast path for continuing to edit the same polygon), and against the **visible subset** (~1,500-2,000 vertices — the scenario's own realistic number, included for context since docs/08 lists picking latency among the measured quantities). The visible-subset fetch is also where the id-indirection hazard M3 diagnostic note 1 and `markers.rs`'s `shuffle` test exist to guard against is checked for real rather than assumed: bbox-filtering by construction makes buffer ordinal diverge from the true global vertex id for (almost) every returned vertex, and that divergence is asserted (`ordinalDivergedFromId`), not just relied upon.

**Deferred origin-swap cost, finally measured.** M2's diagnostic notes flagged this as unmeasured: "the same swap over P1's 10M points is ~20M float writes on the canvas thread — a near-certain dropped frame... belongs to M4/M5." With the full P2 static buffer loaded and idle, a forced re-centre crossing (small threshold, same mechanism as M2's own forced-crossing test) rebuilds the full ~10M-vertex offset buffer synchronously; expected to blow the ≤16 ms budget given M1.5 already measured full-10M-point *render alone* at ~130 ms and this rebuild is a separate ~20M-write cost on top. If it does, the one mitigation tested is a **chunked CPU-side rebuild** spread across `requestAnimationFrame` calls (~200k vertices/chunk, ~50 chunks) rather than an off-thread Web Worker — chosen to avoid Worker/Vite-bundling setup this spike has no other need for, named explicitly as a choice of *a* mitigation, not *the only possible* one. Measured: each chunk's wall time (expected to individually clear budget), total wall-clock time to complete the rebuild, and — separately, since deck.gl has no partial-buffer-upload API — the cost of the single final GPU upload+render frame once the chunked rebuild completes (chunking the CPU loop is not assumed to also solve the upload-frame cost; that is checked, not inferred).

**24-bit picking ceiling** (M3 diagnostic note 2: `encodePickingColor` silently truncates past index 16,777,214 — 16,777,215 features/layer). Only the vertex-handle `ScatterplotLayer`s are `pickable: true`; nothing else consumes picking-index budget. The full-P2 vertex layer holds exactly 10,000,000 features — **59.6% of the ceiling**, the same order of headroom P1 already runs at (60%). The visible-subset (~2,000) and overlay (100) layers are trivially under it. Forward-looking constraint, not a finding: a P2 much larger than M4's declared scale would need either multiple picking passes (index ranges reassembled across layers) or coarser, polygon-level (not vertex-level) picking — one layer suffices only up to ~16.7M vertices.

**Scope limits named up front, not discovered later:**

- The server holds P2 behind a single `Mutex` (`Arc<Mutex<P2Dataset>>`); a long-held lock from the O(100k) bbox scan overlapping a concurrent `commit_vertex_edit` is architecturally possible but not exercised by this harness — single interactive session, no concurrent request in flight during a drag.
- The chunked rebuild is not cancellable mid-flight: if the origin threshold is crossed again while a chunked rebuild is in progress, this spike does not abort/restart it (docs/01 principle 7 asks for cancellable operations generally; this spike's chunking solves the block-the-canvas problem for a single rebuild, not composability of overlapping rebuilds).
- Full-P2-visible drag, and the full-scale commit cost derived from the same operation as origin-swap, are reported findings — not graded against ≤16 ms, per the framing above.
- Several parameters here are smaller than they would otherwise be — full-P2-visible drag's target sample count (20, not the 150 used for the graded visible-subset case) and pick-to-grab-latency's sample count (12, not 20) — and the origin-swap test runs earlier in the harness than its place in the report's own narrative order would suggest (right after the full P2 fetch, before the pick-latency and second drag-benchmark phases). None of this is arbitrary: it is the accumulated result of a real investigation into a reproducible smoke-testing failure on this machine (Windows 10 22H2, Intel UHD 630 / ANGLE-D3D11), whose root cause was **not** conclusively identified, named here rather than silently avoided:
  - Repeated runs consistently stalled somewhere in the harness's tail end, at a roughly fixed wall-clock offset from launch (~17-20 s) — not at a fixed iteration count of any one operation. A sustained `requestAnimationFrame` loop rebuilding a pickable 10M-feature layer every frame stalled at this mark in one run; a pure-CPU chunked array rebuild with **no WebGL calls at all** stalled at the same mark in another; a single-shot GPU buffer reupload stalled there in a third. That rules out any one specific operation as the cause.
  - Once stalled, not just `requestAnimationFrame` but a 30 s `setTimeout` safety guard also stopped firing, meaning the JS event loop itself was blocked, not merely throttled — consistent with the renderer process being stuck inside a synchronous call (plausibly a GPU/driver-level stall, e.g. Windows TDR recovery on the integrated GPU) rather than any script-level bug or scheduler starvation.
  - Explicitly disabling Windows process power throttling (`SetProcessInformation` / `PROCESS_POWER_THROTTLING_EXECUTION_SPEED`) on both the host process and every `msedgewebview2` subprocess did not prevent the stall, ruling out OS background-window power management as the cause.
  - Reducing an individual operation's iteration count did not reliably prevent the stall (halving the chunked rebuild's iteration count from ~50 to ~15 chunks made no difference), but reordering the harness so the *total* elapsed time before the historically-riskiest operations is shorter did — this is the strongest evidence for a wall-clock/cumulative-session trigger over a per-operation one, though the mechanism remains unconfirmed and the fix is empirical, not root-caused.
  - `DRAG_BENCHMARK_TIMEOUT_MS` (30 s) bounds both drag benchmarks, the chunked rebuild, and the full-scale commit reupload, so a recurrence degrades to a `timedOut`/null result instead of blocking the harness *when the JS event loop is still running* — but per the point above, the observed failure mode can freeze that loop entirely, in which case this guard cannot fire either. That gap is real and unresolved, not papered over. If the tester agent's independent run hits this same stall, that is itself corroborating data for this finding, not a harness bug to fix silently.

None of these individually, nor all six summed, gets anywhere near closing the ~120 ms gap between the reference and the 16 ms/60 fps budget.

**3. Visible-count scenario** — `?bbox=` does an unindexed linear scan (`src-tauri/src/p1.rs` `arrow_ipc_bbox`) over the same 10M-point dataset, sized via a uniform-density assumption for ~1M points, then benchmarks pan/zoom over just that subset.

| | Run 1 | Run 2 |
|---|---|---|
| Points selected | 999,841 / 10,000,000 | 999,841 / 10,000,000 |
| Fetch (bbox scan + transfer) | 476.2 ms | 492.7 ms |
| Parse | 21.2 ms | 11.5 ms |
| Frame time p50 / p95 | 16.7 / 17.2 ms | 16.7 / 17.1 ms |

p50 lands back at the 60 fps/vsync floor — essentially identical to the n=1M point on the scaling curve (16.7 ms both places, all four runs). Caveat: the bbox filter's own O(n) unindexed scan cost (~0.5 s fetch here) is a confound on this experiment's numbers — it shows "does a smaller *rendered* set help," not "is server-side viewport filtering itself cheap." A real spatial index would be needed to answer the latter, and that's undesigned (M5's job).

**4. Streaming first-pixels** — Tauri 2.11.5's `register_uri_scheme_protocol` only resolves one complete response per request; no lower-level streamed-body API exists in this version (confirmed while building this diagnostic — worth carrying into M5's transport decision directly). Simulated instead via 40 sequential fetch+parse+render round trips over disjoint ~256k-row slices, each its own self-contained Arrow IPC message (own schema message per chunk, unlike real IPC streaming's schema-once framing), accumulating into a growing binary attribute buffer.

| | Run 1 | Run 2 |
|---|---|---|
| Time to first batch rendered | 143.7 ms | 138.6 ms |
| Time to stable view (all 40 in) | 4724.6 ms | 4696.7 ms |

First-batch-rendered is far closer to the <100 ms budget than M1's monolithic transfer (~2200–2900 ms) — roughly 15–20× better — though still ~40–45 ms over it. Time-to-stable-view is *slower* than M1's single-request transfer of the full 10M points, as expected: 40 round trips add per-request overhead (including a re-sent schema message each time) that a real backpressured streaming connection wouldn't pay. Caveat: this is a request-level simulation of chunking, not real streaming — it answers "does splitting the payload help first-pixels," not "what will the real ADR-004 transport cost," which is still undesigned and is M5's job. The `?n=`/`?bbox=`/`?chunk=` query params used across all four experiments here are spike-local diagnostic scaffolding, not a proposed SKP wire protocol shape.

Reading the four together: the scaling curve is flat at the vsync floor through 1M points and then grows roughly linearly with point count from 1M to 10M, not flat — that rules out a fixed per-frame framework tax as the dominant cost. The toggle deltas are all small (single-digit ms on a ~140 ms baseline) and don't sum to anything close to the gap, which rules out any one of these particular deck.gl/WebGL settings as the culprit. The visible-count experiment, despite its own scan-cost confound, recovers the 60 fps budget almost exactly by cutting the rendered set to roughly the same size as the n=1M scaling-curve point — i.e., cost tracks *points rendered per frame*, and reducing that count is the one lever tried here that actually closes the gap. Verdict: this reads as **GPU-bound work that scales with point count** (per-point/per-instance processing cost, not a fixed framework overhead and not explained by any single cheap toggle), with **workload-shaping** (rendering fewer points per frame, via viewport culling or level-of-detail) as the practical mitigation confirmed to work here — the two aren't competing explanations so much as cause and cure: M2–M5 should treat "reduce points rendered per frame" as the primary lever, and treat server-side spatial indexing and a real streaming transport (both still undesigned) as the open questions that determine whether that lever can be pulled cheaply.

## Diagnostic notes (M3) — picking-buffer surprises under offset-relative rendering

Recording what the picking path does that the rendering path did not prepare you for. This is an explicit M3 deliverable, not a milestone: no pass/fail verdicts below, and the results table is unchanged. Same hardware, harness and three bit-identical runs as the M3 rows.

**1. `PickingInfo.coordinate` is a local-frame value wearing a coordinate's clothes — and it is untagged.** This is the concrete form of the local-frame leak the M2 review flagged, and it is the single reason the measured path is `pick id → host-side f64 lookup` rather than unprojecting the cursor. deck.gl unprojects through the viewport, and under offset-relative rendering the viewport is itself in the local frame, so `info.coordinate` comes back as metres from a renderer-internal origin — a bare `[x, y]` with no frame attached, structurally indistinguishable from an EPSG:2056 pair. **Two distinct error terms live here, and conflating them would make a *type* error look like a rounding error:**

- **(i) Frame error — 3 116 272 m.** Taking the raw value at face value, as any caller reading a `[x, y]` would: a sampled raw value is `[4.894791666666664, −3.042708333333324]` where the real easting is ~2.6×10⁶. `rawCoordinateIsLocalFrame: true` on every run. The error is not a precision artefact; it *is the origin*. Computed independently, the frame origin at the NE probe has magnitude 3 116 271.7 m against the harness's worst-case 3 116 272.08 m — the 0.4 m difference is just the click's own offset within the local frame. 3.1×10⁸ times the 1 cm budget, and a fixed offset rather than noise, so no amount of averaging or zooming touches it.
- **(ii) Residual after correctly restoring the origin — 0.1789 m = 1.352 px**, dead-centre clicks only (the 1–3 px offset clicks are reported separately at 0.4770 m = 3.606 px, since unprojection there correctly recovers the *cursor*, not the feature; folding them in would let "the user clicked 3 px off" masquerade as a pixel-resolution limit). Still **~18× past the 1 cm budget**. But the mechanism is worth naming precisely, because it is *also* not precision: recomputing `hypot(frac(x), frac(y))` over the harness's own dead-centre click positions — the harness floors each predicted position to an integer pixel before picking — gives a worst case of **0.1789177761753911 m**, against the measured **0.1789177761906838 m**. Those agree to **1.5×10⁻¹¹ m**. So the residual is *entirely* integer-pixel click quantization; deck.gl's unprojection arithmetic contributes nothing measurable at f64. The conclusion the metric definition drew is strengthened rather than weakened: at 1:500, 1 cm is 0.0756 px, so even a hypothetical perfect sub-pixel cursor would leave ~0.5 px = 0.066 m, still **6.6× the budget**. Unprojection cannot reach centimetres here at any implementation quality.

By contrast the host-side reply is frame-tagged on purpose — `resolve_pick` returns `{crs: "EPSG:2056", e, n}` and `wrongCrsTagSeen: false` on every run. That asymmetry is the finding: the path that crosses the Rust boundary names its CRS, and the path that comes out of the renderer does not (docs/01: CRS is a type).

**2. deck.gl's pick index is 24-bit, with a silent ceiling at index 16 777 214 (2²⁴ − 2) — 16 777 215 features per layer.** Read from deck.gl 9.3.7 source (`@deck.gl/core` `dist/lib/layer.js`), **not measured here**, in the same spirit as M2's shader auto-offset note — a version bump invalidates the explanation: `encodePickingColor` writes `(i + 1)` into an RGB triple as `(i+1) & 255`, `((i+1) >> 8) & 255`, `(((i+1) >> 8) >> 8) & 255`, and `decodePickingColor` reads `i1 + i2·256 + i3·65536 − 1`. Past that index the third byte truncates the bits above 24 and a pick returns a **wrong-but-plausible index with nothing raised** — the same silent-wrong-answer shape as the ordinal-vs-id hazard, one level lower. P1's 10M points sit at ~60 % of that ceiling, so the spike's own headline dataset fits with less headroom than is comfortable, and M4/M5 should treat the ceiling as a real constraint on any "one layer, all the features" plan rather than an abstraction.

**3. The picking footprint is bigger than the styled footprint.** Class (c)'s discrimination curve is only reproducible (all 27 cells, exact counts and flags) with an effective radius of **1.49–1.57 px** against a styled `getRadius: 1` px — roughly half a pixel of rasterization/antialiasing spread that the picking pass keeps and the visible disc fades out. Fitted outside the harness, so corroboration rather than measurement. The practical consequence is that **picking resolution is a style-dependent property**: two features are distinguishable or not depending on how big they are drawn, and where footprints overlap the picking buffer keeps whichever drew last — a draw-order artefact, deterministic but arbitrary. Any future "pick the nearest feature" behaviour has to be built on top of that, not assumed from it.

**4. Nothing here is a coordinate-precision effect, and that is itself the result.** Every M3 surprise above is a frame error, an input-resolution limit, an encoding ceiling or a style artefact. At the local-frame magnitudes offset-relative rendering produces (metres, not megametres), the f32 ULP is ~5×10⁻⁷ m — five orders of magnitude below both the smallest separation tested (0.10 m) and the 0.18 m unprojection residual. The precision question M2 answered stays answered; what M3 exposes is that the *plumbing* around picking has its own failure modes, and they fail silently by default.
