2. ADR-021 adjacency — DuckDB extension autoload is ON by compiled default in the engine.
Fact (verified locally, cargo registry): libduckdb-sys 1.10505.0 build_bundled_cc.rs:96-97 compiles DuckDB with `DUCKDB_EXTENSION_AUTOINSTALL_DEFAULT` and `DUCKDB_EXTENSION_AUTOLOAD_DEFAULT` set to "1". engine/src sets no `autoinstall_known_extensions` / `autoload_known_extensions` (grep: none); connections are `Connection::open_in_memory()` with only `SET enable_geoparquet_conversion=false`. ADR-021's property ("admission performs no runtime extension fetch of any kind") holds today because `json` is built in — it holds by content, not by configuration: any DuckDB-side reference to a known-but-not-bundled extension function would trigger an install attempt (filesystem write + network fetch). No such reference exists today; the admission allowlist bounds caller SQL. Nothing in ADR-021 is wrong; it is narrower than the engine's actual configuration.
Options:
  1. Harden by configuration now (Recommended): a small engine PR setting `autoinstall_known_extensions=false` and `autoload_known_extensions=false` at every connection open (the pool's existing SET site), with a test that a non-bundled extension function fails closed (catalog error, no install attempt); short preregistration (cause → fix → test) before code; reviewer-gated; and an appended amendment to ADR-021 recording the setting as part of the property (append only — the ADR is not rewritten).
  2. Record only: append the fact to ADR-021 as a note; no engine change now.
  3. Fold it into Brief A's engine work (P3–P6) rather than a separate PR.
