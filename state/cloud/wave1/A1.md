### Finding A1-1
Claim: The data plane accepts a WebSocket upgrade whose `Origin` header is present and names a foreign origin, as long as that header contains a non-ASCII byte and the request also sends `sec-fetch-site: same-origin`. It treats such a header as if no `Origin` were sent.
Suggested severity: S3
Code path: `protocol/data-plane/src/server.rs:290` (`headers.get("origin").and_then(|v| v.to_str().ok())` turns a present header with a byte in 0x80–0xFF into `None`) → `server.rs:291-292` → `protocol/data-plane/src/session.rs:107` (`None => sec_fetch_site == Some("same-origin")`) → admitted. It then reaches the token check at `server.rs:296-303`.
Reproducer: `protocol/data-plane/tests/origin_header_encoding.rs` on cloud/wave1-A1. Run `cargo test -p spatial-data-plane --test origin_header_encoding`. Observed:
- `control_a_foreign_ascii_origin_with_a_same_origin_claim_is_refused ... ok`
- `a_stated_non_ascii_origin_must_be_refused_like_any_other_foreign_origin ... FAILED`, panicked at line 75: "a stated Origin that is not the expected one was ADMITTED…"
- `the_same_holds_for_a_host_declared_origin_adr_020 ... FAILED`, panicked at line 87: "with expected_origin declared (ADR-020), a stated non-ASCII foreign Origin was ADMITTED"
Guarantee violated:
- docs/09 "Local listening sockets" says connections are admitted on the token "plus exact-match `Origin` validation".
- `session.rs:96` documents "A stated `Origin` must match exactly".
- ADR-020 Decision: "Exact-match comparison is unchanged."
Evidence: The only difference between the passing control and the failing cases is one `\xff` byte appended to the same foreign origin. The control is refused and the non-ASCII variant is admitted. This holds both for the port-derived origin and for a host-declared origin (`expected_origin: Some("http://localhost:5180")`). A valid token was presented in every case, so the token barrier itself is not bypassed.
False-positive check:
- Searched KNOWN-LIMITATIONS.md and DECISIONS-PENDING.md for `to_str`, non-ASCII, obs-text and `sec-fetch`. The only hit, DECISIONS-PENDING.md:1547, says "the `sec-fetch-site` fallback unchanged" and does not mention this conflation.
- The existing tests in `session.rs:152-185` and `kernel/tests/skp_admission.rs` call `request_allowed` with `&str` values or send ASCII headers. None covers a header that fails `to_str`.
- Impact is bounded: docs/09 itself says origin validation is no barrier against local processes, and browsers always send ASCII origins. So this is a deviation from the stated contract that I cannot show is exploitable from a browser.
Confidence: proven

### Finding A1-2
Claim: Page script can write forged, extra records into the session log through `binding_log_session_event`, because the `level` argument goes into the log line with no newline escaping. Also, neither `level` nor `message` has `\r` escaped.
Suggested severity: S3
Code path: `frontends/shell/src-tauri/src/lib.rs:481+` (`commands::binding_log_session_event` registered in `generate_handler!`) → `frontends/shell/src-tauri/src/commands.rs:157-159` (`level: String, message: String` from JS, passed straight to `state.append`) → `frontends/shell/src-tauri/src/state.rs:50` (`format!("{ms} {level} {}\n", message.replace('\n', "\\n"))`, which escapes `\n` in `message` only).
Reproducer: code path only. The shell crate cannot be built here without webkit2gtk.
Guarantee violated: no ADR states a security guarantee for this log. It breaks the function's own documented contract at `state.rs:41` ("Append one line: `<unix-ms> <level> <message>`") and `state.rs:48-49` ("A single-line record, even if `message` itself contains a newline"). The log is the persistence half of ADR-010 rule 7. docs/09 records `"csp": null`, so any script that reaches the page can call this command.
Evidence: read at the baseline — `level` is interpolated raw, and only `'\n'` in `message` is replaced.
