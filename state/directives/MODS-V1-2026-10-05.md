# Guardian v1 and Evidence Recorder v0.1 — fixes, a refusal log, three new rules and a repeat-runner (brief, 2026-10-05)

*Fable, 2026-10-05, on the human's direction of the same date: keep testing the mods by fixing them and giving them more to do. The custodian files this under `state/directives/` with the human's covering line. It authorises building and gating two pieces in the governance lane, one after the other: `evidence-recorder-v0-1`, then `guardian-v1`. Repository facts were read at main 4398a779.*

**Both mods are installed by reference.** `claude plugin list` reads each from its folder under `tools/mods/` in the main checkout (Guardian's Amendment 8, E0; the Recorder's Amendment 5, E0). So a merge changes the live mod at the next reload. **Each merge is therefore the security-posture change itself: it waits for the human's typed approval, given after both gates and before his click, and naming the live checks he allows.**

## 1. What stays, and the one thing that changes

- **Guardian only refuses, and fails closed.** It never approves a call, rewrites arguments, submits a prompt, calls a model or makes a network request.
- **The Recorder only observes.** It never refuses, rewrites, retries or answers a call, adds nothing the model reads, and returns every result exactly as produced.
- **No mod installs or enables anything.** CI and the gates stay, because cloud sessions and edits on GitHub never pass through a local mod.
- **The one change of principle:** Guardian v1 writes one local log line per refusal (§2.2). Its README sentence saying it writes no file is corrected in the same piece.

### 2.2 The refusal log

- **What:** every refusal appends one JSON line to a folder outside the repository: the time, the rule id, the tool, the agent type, the sha256 of the refused command or path, and Guardian's reason text. It records no command, no path and no content.
- **Why:** false alarms and real catches are counted, not remembered. The v0 brief's "each false refusal is logged" becomes mechanical.
- **Safety:** the write is attempted only after the refusal is decided. A failed write changes nothing, and nothing is written for an allowed call.
- **Standing:** a log line is not citable evidence. Window item E decides that question for recorder lines, and the same answer applies here.
- **P0** confirms the folder (beside the Recorder's log root) and the `validate` calls line with the write on it.

### 2.5 Acceptance and stop

**Acceptance:** every test passes; `validate` shows only what the form declares; then two weeks after the merge, or the next six gated pieces, whichever comes first, with false refusals counted from the log. Each one is narrowed through the usual process.

**Stop, and the human disables it in `/plugin`, if:**
- it lets through a call it should refuse;
- a false refusal blocks a flow the human performs through the custodian;
- `validate` shows a call the form does not declare;
- the log write ever changes a decision.

## 3. Evidence Recorder v0.1

### 3.1 What it answers

After about five hours live on 2026-10-04 the Recorder held four records, all from the custodian's own probes (Amendment 5). The two Phase R campaigns ran their tests in shell loops, which §2.2 of its form leaves not approved, so no real test run was recorded. One of the four records reads `unavailable`: its git calls took 4276 ms against `PROCESS_TIMEOUT_MS` of 2000.

### 3.2 The repeat-runner

- **One script,** in `scripts/evidence/` (the form names it): `node <script> <n> -- <command>`. It runs the command n times in sequence, without a shell, prints one line per run with its index and exit code, prints a summary, and exits non-zero if any run failed. It never retries, never runs in parallel and judges nothing.
- **One new matcher row:** the call is approved when the part after `--` is itself approved by rows A1 to A4. The record gains the repeat count.
- **The brief rule is extended** (question round 50, item 1): testers and workers run a repeated evidence run through the script, never through a shell loop. This is in the human's covering line (§5, item 5).
- The script has its own tests in the scripts suite.

### 3.3 Write latency

This folds in the proposed node `recorder-write-latency-measure`. The form declares how the write's latency is measured, and a new live row with its own sample, before that sample is taken (Amendment 2, C2-d). E5 stays a lower bound and is not rescored.

### 3.4 The wait before a command

- **Required:** the Recorder's total wait before a command has one declared ceiling across all its git calls. Reaching it yields `unavailable`, never a longer wait. Today the calls run in series, each with its own 2000 ms.
- **P0 measures** the identity's cost on a cold tree (a new worktree; the first call after a build) and on a warm one. If cold trees are the cause, the form proposes the remedy as an OPEN item.

### 3.5 P0, tests, gates, live checks, evaluation

**P0:** the script's argument handling on Windows with no shell; the matcher row; where the previous write's duration can be read; the cold and warm costs.

**Tests,** one recorded mutation each:
- the script runs n times, reports each exit and never stops early;
- the matcher approves the script with an approved command, and not with any other;
- the record carries the repeat count;
- the ceiling yields `unavailable`;
- every result still passes through byte for byte.

**Gates:** the reviewer and the architect. Full form.

**Live rows after the merge and a reload,** each run only if the typed approval names it:
- **E8:** a scratch `node --test` repeated three times through the script yields one record with a repeat count of 3.
- **E9:** the write-latency sample, as the form declares it.

**Evaluation:** the v0 window continues (two weeks from 2026-10-04, or six gated pieces). Added measures: the share of repeated evidence runs that have a record, counted from the first piece after the merge; the `unavailable` share; the write latency. The stop conditions are unchanged.
