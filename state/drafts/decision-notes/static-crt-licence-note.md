## Summary (two lines)

**(i) NOTICE set — PARTLY CONFIRMS.** The CRT does join the notice set, but under **ADR-030's own reopen condition**, not because Microsoft's terms demand a notice: no fetched Microsoft term requires attribution for the CRT; and the premise that `libcmt.lib`/`libvcruntime.lib`/`libucrt.lib` appear on the VS 2022 Distributable List is **refuted** (that list contains no `.lib` entry at all).
**(ii) System Library — NOT CONFIRMED (contested; this is the stop condition). (iii) Excluded License — CONFIRMS, conditionally:** the clause bites only on *source code* distribution, so it does not on its face forbid shipping CRT object code inside an AGPL program — but only while (ii) holds, and two other Microsoft conditions (a flow-down requirement; the runtime EULA's own combination ban) are unresolved against AGPL §10.

## (i) Does the static CRT join the NOTICE set under ADR-030?

**Yes, but by our rule, not theirs.** ADR-030's appended note §4 reopens for *"any further third-party set a conveyed artifact carries that no build manifest reports"* (`ADR-030:…` Appended note, item 4). A statically linked CRT is exactly that: no esbuild metafile, Vite manifest or `Cargo.lock` reports `libcmt.lib`. Microsoft's own docs confirm what static linking does (S8): *"Static linking binds the library code into your application"* and *"link the library object code directly into the application"*. So the executable would carry Microsoft object code that the three generators structurally cannot see — ADR-030's reopen condition, met on its face. **(Reasoning, not a sourced legal claim.)**

**What the terms actually require of a distributor.** No fetched Microsoft term requires an attribution or notice *entry*. What they require is: S2 — *"add significant primary functionality to it in your applications"* and *"require distributors and external end users to agree to terms that protect the Distributable Code"* … *"at least as much as this agreement"*. L1 adds *"Display your valid copyright notice on your programs"* and forbids *"Alter any copyright, trademark or patent notice in the Distributable Code"*. S3 forbids *"remove, minimize, block or modify any notices of Microsoft or its suppliers in the software"*. **Paraphrase:** these are *don't-strip* and *flow-down* obligations, not an attribution obligation; an ADR-030 entry satisfies the spirit and violates none of them.

**Where the expected posture is refuted.** The ruling assumed the Distributable List names the static libraries. It does not. S1 was searched mechanically: **zero** matches for `libcmt`, `libvcruntime`, `libucrt`, "static librar", and its only `.lib`-path line is `…\atlmfc\lib\[arch]\mfcmifc80.dll`. Its "Visual C++ Runtime Files" section lists only `Microsoft_VC143_*.msm` merge modules and the `[VisualStudioFolder]\VC\redist` folder — *"copy and distribute with your program the unmodified form of the files listed below"*. **So an express VS-side grant covering `libcmt.lib`/`libvcruntime.lib` object code was not found.** The Windows SDK side *is* express, for `.lib` files (L1): *"For any Distributable Code having a filename extension of .lib, distribute only the results"* … *"of running such Distributable Code through a linker with your program"* — which reads squarely onto `libucrt.lib`. **[unverified]** whether `libucrt.lib` is on the SDK EULA's own "listed below" Distributable Code list: that list sits in an RTF field the extraction did not render.

## (ii) The System Library reading under AGPL-3.0 §1

S4, §1, verbatim in fragments: *"\"System Libraries\" of an executable work include anything, other than the work as a whole"* that *"(a) is included in the normal form of packaging a Major Component"*, *"but which is not part of that Major Component"*, and *"(b) serves only to enable use of the work with that Major Component"*, *"or to implement a Standard Interface for which an implementation is available to the public"* *"in source code form"*. "Major Component" is *"a major essential component (kernel, window system, and so on) of the specific operating system"*, *"or a compiler used to produce the work"*. The exclusion itself: Corresponding Source *"does not include the work's System Libraries"*.

**Where it holds.** MSVC is *"a compiler used to produce the work"* — the Major Component limb is not in doubt.

**Where it is contested — and it is the stop condition.** The only FSF text on point (S5, `#WindowsRuntimeAndGPL`) answers the **dynamic** case: *"the runtime libraries are \"System Libraries\" as GPLv3 defines them"*, so *"you don't need to worry about including their source code with the program's Corresponding Source"*. It then draws the line: *"You may not distribute these libraries in compiled DLL form with the program"*, because libraries *"can only qualify as System Libraries as long as they're not distributed with the program"*. **Paraphrase:** static linking is the case where the runtime's object code travels *inside* the conveyed file — further along that line, not behind it. The FAQ nowhere addresses static linking, and no FSF text was found that does. **[unverified: any FSF or court statement on a statically linked MSVC CRT.]**

**One honest correction.** The FAQ attributes its limit to the licence — *"the GPL says that"* — but AGPL-3.0 §1 as fetched (S4) contains **no** sentence conditioning System-Library status on not being distributed with the program; mechanically checked, "System Libraries" occurs twice in S4, at the definition and at the Corresponding-Source exclusion, and neither carries that clause. The gloss is the FSF's reading of limb (a). So the contest is narrow and real: **does an object-code copy inside the covered work still satisfy "is included in the normal form of packaging a Major Component, but which is not part of that Major Component"?** Limb (b)'s second branch (a Standard Interface — the C standard library — with public source implementations) may carry the reading on its own; **[unverified: no source found either way].**

**Note what today's build already assumes.** v0.1.0 links `MSVCP140.dll` dynamically and ships no copy of it (`RELEASE-0.1.md:1168`; entry 69) — the exact configuration the FAQ blesses. The static CRT is a change *away from* the sourced-safe case, not toward it.

## (iii) The "Excluded License" clause — can the static CRT ship inside an AGPL program?

S2, verbatim, under "Distribution Restrictions" — you may not: *"modify or distribute the source code of any Distributable Code so that any part"* *"becomes subject to an Excluded License."* And the definition: *"An \"Excluded License\" is one that requires, as a condition of use, modification or distribution of code, that"* *"(i) it be disclosed or distributed in source code form; or (ii) others"* *"have the right to modify it."* L1 carries the older wording to the same effect (its extraction reads *"Modified or distribute the source code of any Distributable Code…"*, *"The code be disclosed or distributed in source code form; or"* — the leading word is an artifact of the RTF field extraction and is flagged rather than smoothed).

**Reading, labelled as reading, not advice.** AGPL-3.0 is unambiguously an Excluded License by that definition. But the restriction's object is **the source code** of Distributable Code. We would convey the CRT's **object code**, linked, and would not place Microsoft source under AGPL. On the fetched wording, the clause does not forbid it. Two riders: **(a)** the safety is downstream of (ii) — if the System Library reading fails, AGPL §1 would pull the CRT's source into Corresponding Source, which is both impossible and precisely the Excluded-License trigger; **(b)** S2's flow-down requirement (*"require distributors and external end users to agree to terms that protect the Distributable Code"* … *"at least as much as this agreement"*) sits against AGPL §10: *"You may not impose any further restrictions on the exercise of the rights granted"* (S4). Whether the flow-down is a further restriction *on the covered work* — or only on a System Library that the covered work's licence never reached — is the same question as (ii), arriving from the other side. **Also unresolved:** S3, the runtime's own EULA, forbids the user to *"provide the software as a stand-alone offering or combined with any of your applications"*; **paraphrase:** that is the end-user licence for the installed redistributable, and the developer's distribution right lives in S2, not S3 — but with the VS-side `.lib` grant not located (see (i)), the two do not cleanly compose. **[unverified]**

**So: the terms as sourced do not restrict static distribution outright, and the piece is not stopped by (iii). It is stopped by (ii)** — the System Library reading is stated but not confirmed, and the one authority on point reasons against it. Per the ruling's own words, this returns to the human.

## Decision points

1. **Does the System Library reading hold for a *statically linked* CRT?** Your reading, or counsel's per ADR-009's Caveat. No source confirms it; S5's stated rationale reads against it. **If no, the build piece does not proceed and entry 69 stays at option (a) (declare) for v0.1.1.**
2. **AGPL §10 vs the flow-down.** Is *"require distributors and external end users to agree to terms that protect the Distributable Code"* a further restriction on the conveyed work, or a condition outside it?
3. **Where is the grant for `libcmt.lib` / `libvcruntime.lib`?** The VS 2022 Distributable List names no `.lib`; the Windows SDK EULA's `.lib`-through-a-linker clause covers `libucrt.lib` only. Accept the gap, locate the Build Tools EULA (404 today), or ask counsel.
4. **Does ADR-030 formally reopen** for a conveyed set that *no* build manifest reports and whose enumeration source is a licence page rather than an upstream tree — i.e. what "hash-pinned enumeration" means here (the Appended note's §4 wording), and whether the notice's scope sentence must change.
5. **If (1) is "hold":** does v0.1.1 ship the dynamic CRT with entry 69 (a) (declare in KNOWN-LIMITATIONS 15 + QUICKSTART), or bundle the redistributable (entry 69 (c), which reopens ADR-030 for a separately conveyed artifact)?
