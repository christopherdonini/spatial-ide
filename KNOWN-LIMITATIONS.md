# Known limitations — Spatial IDE v0.1.0

*What this release does not do, declared rather than discovered. Every line below is true of the
artifact that carries the v0.1.0 tag — the installer built from this branch, walked through by the
operator on a clean Windows account (`frontends/shell/MANUAL-WALKTHROUGH.md` Part M; the sittings are
recorded verbatim in `RELEASE-0.1.md` Amendments 15–18). Part M was run across two builds: the rows
whose code paths this build changed (M1–M5, M7, M12 mode 3, M14, M15 and the hover row) were re-run
on it; the rows it did not touch (M6, M8, M9, M10, M11, M12 modes 1–2, M13) stand from the candidate
build `998be05`, with `git diff --stat 998be05 13471a9` as the proof that nothing under their paths
changed — the classification and that diff are Amendment 17's. Each line carries its source in an HTML
comment so it can be checked. No line here states a speed, a duration or a rate: this release makes
no performance claim at all (`docs/08_Testing.md`).*

2. **Two pinned coordinate reference systems, and three refusals by name.** The catalog the app
   carries holds exactly two entries, in this order: `epsg-2056` — **CH1903+ / LV95** (EPSG:2056),
   and `epsg-3857` — **WGS 84 / Pseudo-Mercator** (EPSG:3857). Those two are what the app can supply
   a definition for, and the only choices the assertion panel offers. A file that declares its own
   CRS is admitted on that declaration, and only if the declaration establishes an easting-first axis
   order. The app never guesses a CRS, never applies a default, and never fetches a definition from
   the network.

   - **A file whose `geo` metadata has no `crs` key is refused** — GeoParquet's OGC:CRS84 default is
     deliberately not applied — and so is **a file whose `crs` key is present and explicitly
     `null`**. Both reach the same typed refusal, code `engine.crs_undeclared`: *"refused: the file
     declares no CRS and none was asserted by the caller (no `geo` metadata CRS on the primary
     geometry column). This engine does not apply GeoParquet's OGC:CRS84 default (docs/05, no silent
     conversion)"*. The app then offers to let you **assert** a CRS — a pinned catalog entry or a
     pasted PROJJSON definition — and records the assertion as a claim; nothing is saved.
     <!-- engine/src/geoparquet.rs:94-104 (the three distinguishable states: object = declared, null = not declared, absent = default NOT applied); engine/src/error.rs:176-179 (the message); MANUAL-WALKTHROUGH.md B2 (the message verbatim as the panel shows it), I1 (the assertion form) -->

   - **A CRS whose definition declares latitude first is refused, not reinterpreted** — code
     `engine.axis_order_unsupported`: *"refused: established axis order is northing,easting; this

   **On `main` (not the v0.1.0 artifact above).** For a file that declares GeoParquet version 1.0.0 or 1.1.0, two of these refusals no longer happen. A file with no `crs` key opens as OGC:CRS84, which is the format's own rule, and the summary records it as `crs:format-default`. A file whose CRS declares latitude first, EPSG:4326 included, opens with the coordinate order the format lays down, recorded as `axis:format-override`; its declared order is kept as a recorded fact and no coordinate is transformed. Still refused: a `crs` key that is present and `null`, a latitude-first or northing-first CRS that you assert yourself, and either case in a file of any other GeoParquet version. Also refused: a file with no `crs` key whose coordinates the open-time check (item 22) finds outside ±180/±90, because they cannot be longitude and latitude. The code is `engine.format_default_contradicted`. The app then offers the CRS assertion form, so you can assert the CRS the file is really in.

3. **Identity must already exist in the file, as a single integer column.** The app uses the file's
   own `id` column, or one column you declare a mapping from, and scans it for uniqueness at open.
   The column must be an integer type that widens into `u64` without transformation; anything else is
   refused — *"refused: `<column>` cannot serve as stable feature identity — type is `<type>`;
   identity must be an integer that widens into u64 without transformation. …"*. Composite keys are
   not supported, and no hash, dictionary index or row ordinal is ever synthesized in their place.
   <!-- engine/src/identity.rs:196-217 (admit_column_type: the admitted integer types and the refusal detail); engine/src/error.rs:234-238 (IdentityUnusable Display); ADR-016; ADR-010 rule 2; MANUAL-WALKTHROUGH.md A3 (`file:id — verified-at-open-full-file`), M4 (the same summary on the packaged build) -->

   **On `main` (not the v0.1.0 artifact above).** A single file that has no `id` column and no declared mapping opens instead of being refused. Its features are identified for that session only, by their position in the file, and the summary says so. That identity does not survive a reopen or a change to the source, and it is never saved or published. This is the one case in which a row position stands in for identity. The app does not yet offer a way to declare an identity column for a file that opened this way: the declaration form appears only when a file's identity is refused. A file whose `id` column cannot serve is still refused.

5. **The published bundle has declared ceilings, and a whole-file publish predicted above
   `MAX_FEATURES` is refused before anything is written (item 6 names the ceilings no prediction
   covers).** The viewer's ceilings are `MAX_FEATURES` 2000000, `MAX_PARTITIONS` 100000,
   `MAX_RESIDENT_BYTES` 536870912, `MAX_ATTRIBUTE_COLUMNS` 32, `MAX_ATTRIBUTE_DISPLAY_CHARS` 512 —
   declared limits, not measurements. A whole-file publish of a source predicted above `MAX_FEATURES`
   is refused at preflight: *"refused: this publish is predicted to exceed the bundled viewer's declared ceiling
   MAX_FEATURES — limit 2000000, predicted 3300000 — before any bytes were written (ADR-025: refuse,
   typed, at preflight; reopens when a second reader exists). Instead, publish the current-viewport
   bbox instead of the whole file (the viewer's ceilings apply to what a bundle carries, not to what
   the source dataset holds)"*; the approval dialog never opens and no destination is created. A Current view publish is not
   predicted from the whole file: it is refused only if its own rows exceed `MAX_FEATURES`, and that
   refusal comes while the rows are being written, after the approval, with nothing left at the
   destination.

47. **A publish is refused when the bundle would contain a local path, your login name, this computer's name or a credential word, and the check is a pattern search, not a proof.** Before the bundle is moved into place, every file it would contain is searched, including the values of the columns your style uses, for:

53. **A file is refused when it is opened if a name in its `covering.bbox` or its `geo.primary_column` matches more than one of its column names, or names a column the app reads under another name.**
    When a file holds two column names that differ only in the case of the letters A to Z, or two such field names inside one column, the app reads the later one under a changed name, with a suffix added, such as `BBOX_1` for a second `BBOX`; a changed name that meets a name the file already holds is changed again, so the file's own `BBOX_1` is then read as `BBOX_1_1`. The names in a file's `geo` metadata, the paths of its `covering.bbox` and its `geo.primary_column`, are matched against the names the file itself holds, not the changed ones. Each part of a `covering.bbox` path is matched to the file's column names, and to the names of the fields inside a column, without regard to the case of the letters A to Z. Where one part matches two or more of them, such as `bbox` against columns named `bbox` and `BBOX`, the open is refused rather than one of them chosen, even when one is spelled exactly as the path is. Where it matches one, and the app reads that column under a changed name, as for a path naming `BBOX_1` in a file that holds `bbox`, `BBOX` and `BBOX_1`, the open is refused too: the path would not read the column the file names. `geo.primary_column` is judged by the same rule: where it matches two or more of the file's column names without regard to the case of the letters A to Z, such as `geometry` against columns named `geometry` and `GEOMETRY`, or against two columns both named `geometry`, the open is refused, even when one is spelled exactly as the name is. Otherwise it must match one of the file's column names exactly, and where the app reads that column under a changed name, the open is refused the same way. These refusals have the code `engine.geo_metadata` and name the declared name with the file's names it matches, or with the name the app reads that column under. A covering is refused this way even when another of its paths names a column the file does not contain. A covering path that matches none of the file's names names a column the file does not contain, as item 9 says, even when it is spelled like a changed name, such as `BBOX_1` in a file that holds only `bbox` and `BBOX`. A `geo.primary_column` that matches none of them exactly, and is not refused for matching two or more, is refused as `engine.source`, with the same text as before, saying the file does not contain it; that now includes a name spelled like a changed name, such as `GEOMETRY_1` in a file that holds only `geometry` and `GEOMETRY`. In these checks a letter outside A to Z in a different case counts as a different letter. Only the names the file supplies are checked this way: names you supply, such as a column a filter names, are matched as before, against the names the app reads the columns under, and column names in a file that differ only in letter case cause no refusal except in the cases above. A covering path containing U+0000 still opens with that covering unusable, as before, whatever its other paths match.

57. **On Windows, a session can end with no change to the file, when the watch loses coverage.**
    The advisory source-change watch (item 24) reads the operating system's change notifications into a buffer of a declared size. If that buffer overflows, if reading the notifications fails, or if the watch cannot be set up again after a notification that named some other file, the watch reports that it lost coverage. 67. **The Console keeps its newest 256 entries, and one load of a view can add more than two hundred.**
    The Console keeps its newest 256 entries. When it is full, each new entry drops the oldest one, and the Console's label shows how many were dropped. When the first data load of a view completes (after an open, an Apply or a Clear, for example), the map asks for tiles of that view. Each tile is asked for in a request of its own, and each request is an entry. When a tile's load ends, other than by a cancel the app makes (after your Cancel, for example), the app writes a line to the session log, and that write is an entry too. Panning and zooming ask for tiles in the same way. In the app-window tests one such load was at least 110 tiles, which is at least 220 entries. At 220 entries a load the Console holds little more than one load, so the entries before it, the steps you recorded among them, are dropped. Only the entry leaves the Console: the request was already sent, and a recorded step stays in the session's history. A group of entries you have opened closes again when its first entry is dropped.

68. **A filter change made while the previous data load is finishing can leave the new view unfilled until you pan or zoom, and the status line can still say that all features in view are shown.**
    An Apply or a Clear starts a new first data load, and so does any other change of the filter that is applied; applying Colour by can start one too (item 56). If the previous first data load is still running then, the app goes on treating it as the current one for a short moment, until the new load's stream has been set up. When the previous load completes inside that moment, the map can ask for tiles of the view it shows at that instant, under the filter the new load carries, as it does when a first data load of a view completes (item 64). If it does, then when the new load itself completes the map asks for no tiles of the view it shows; it asks for them at your next pan or zoom. Until then the map can show only part of what that view holds, and the status line can say that it is showing all the features in view. This has been reached only in a test that puts the two events in that order by hand; it has not been seen in the running app.
